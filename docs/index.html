comment-guard 講義

給使用 AI coding agent 的團隊：如何把「不要留下低價值註解」從口頭提醒，變成 repo 會自動執行的規則。

1. 問題不是「註解太多」，而是註解留下錯誤訊號

AI 代理常見的壞註解有三類：複述程式碼、記錄修改歷程、以及修改後沒有同步更新的過時註解。真正麻煩的是它們會成為下一輪生成的範例，讓代理以為這是 repo 的慣例。

移除

複述 what

# Convert the date strings to datetime objects 這類註解通常只是把下一行程式翻成自然語言。

移除

記錄修改過程

# fixed per user request、# NEW:、# 已修正 應該進 commit message，不該進程式碼。

保留

解釋 why

資料編碼依據、演算法取捨、外部 API 限制、研究倫理提醒，這些是程式碼自己無法表達的脈絡。

2. 相關文章與討論怎麼支持這件事

來源類型重點對 comment-guard 的啟示
工程實務指南 Google Engineering Practices 建議審查者確認註解是否必要；通常註解應說明程式存在的理由，而不是重說程式在做什麼。 規則檔要明確寫成「why, not what」。
開發者討論 GitHub Community 有開發者回報 Copilot 會產生過多、冗餘、干擾閱讀的註解，且有人希望能單獨關閉註解建議。 單靠提醒代理「不要寫註解」不穩定，需要本地 hook 或 CI。
軟體工程研究 過時註解可能誤導後續維護者；LLM 生成註解也可能包含可被證明不正確的敘述。 先攔截最容易機械辨識的壞註解，再把細緻判斷留給 review。
AI review 研究 針對代理產生的 code review comments，未解決討論常見原因包括錯誤建議與設計決策衝突；冗長複雜的評論較不容易被採納。 工具訊息要短，檢查範圍要窄，避免把風格偏好偽裝成硬性錯誤。

3. 判斷規則

可以保留

  • 說明某段程式為何採用不直覺做法。
  • 記錄資料清理、編碼、欄位對照的研究判斷。
  • 標明外部服務、檔案格式、法規或倫理限制。
  • 公共 API 文件、函式用途、參數契約與例外行為。

應該移除

  • 把下一行程式翻成中文或英文的註解。
  • 只對當次修改有意義的註解。
  • 含有 NEW、FIXED、UPDATED、已修正、依要求 這類歷程字樣的註解。
  • 程式已改，但註解還在描述舊行為。

4. 導入流程

  1. 先掃描現有 repo：tools/check_comments.sh --all，清掉會被 AI 模仿的壞範例。
  2. 固化規則：把 rules.md 寫入 CLAUDE.md 或 AGENTS.md。
  3. 安裝 hook：讓 staged diff 在 commit 前自動檢查。
  4. 加 CI：多人協作或 GitHub repo 建議加 workflow，避免只靠個人電腦設定。
  5. 保留人工 review：工具只能抓固定字樣，複述型註解仍需要人判斷。
